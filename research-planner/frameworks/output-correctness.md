# 산출물 규칙 — correctness와 재량을 가른다

> 출처: Claude Science `skills/figure-style/SKILL.md`의 구조를 이식 (Apache-2.0, 2026-08-03 해부).
> 원문 선언: *"이 스킬은 **체크리스트지 하우스 룩이 아니다** — 프레임·폰트·팔레트는 파라미터다."*
> 이식한 것은 그림 스타일이 아니라 **"무조건 지킬 것과 골라도 되는 것을 문서 상단에서 가르는" 구조**다.

---

## §0 이 문서의 사용법

**§1~§4는 correctness다.** 모든 산출물에 무조건 적용되고 **미적·취향 재량이 없다.**
**§5~§7은 재량이다.** 프로젝트·독자에 맞게 고른다.

산출물을 내기 전에 §1~§4를 한 줄씩 통과 여부로 확인한다. 한 건이라도 걸리면 내지 않는다.

# correctness (무조건)

## §1 데이터 충실성

- **제목·캡션이 주장하는 바를 데이터 전체에 대해 검증한다.** "대체로 ±2%p"라고 썼으면 모든 행이 그런지 확인한다. 헤드라인과 데이터가 어긋나면 어느 쪽이 틀렸든 그 산출물은 독자를 오도한다
- **분석에서 제외한 데이터는 요약·집계에 절대 들어가지 않는다.** 제외했으면 제외 사실과 사유를 남긴다
- **보고서에 적은 수치는 실제 산출물을 실행한 결과와 일치한다.** 하드코딩된 수치가 가장 흔한 실패 모드다
- 반올림·단위 변환을 했으면 **원값에 도달하는 경로**가 남아 있다

## §2 출처와 등급 — **주장 유형별로 요구 수준이 다르다** ★

> 2026-08-03 개정. 이전 규칙은 "verified가 아니면 본문 단정 금지"였다.
> 그건 **리서치 보고서**에는 맞지만 **연구개발계획서**에는 틀린다 — 계획서는 아직 검증되지 않은
> 가설을 어떻게 검증할지 쓰는 문서라, 모든 주장에 실증을 요구하면 신규 주제를 제안할 수 없다.
> 규칙을 버리는 게 아니라 **유형을 가르고 각 유형에 맞는 근거를 요구**한다.

| 유형 | 무엇인가 | 요구 근거 | 표기 의무 |
|------|---------|----------|----------|
| **① 외부 사실** | 세상에 이미 있는 사실 (시장 규모, 선행연구 결과, 법령, 타 기관 성과) | **독립 출처 2개 + 1차 소스 도달.** 기존 verified 규칙 그대로 | 출처·연도·A~E 등급 인라인 |
| **② 전망·추정** | 미래 예측, 시장 추정치 | **출처 1개 + 추정 주체 명시** | "○○에 따르면" — **우리 주장으로 위장 금지** |
| **③ 내부 가정** | 우리가 전제로 삼는 것 (데이터 접근 가능, 장비 가용) | 근거 불필요 | **"~를 전제로 한다"** 명시. 전제가 깨지면 어떻게 되는지 함께 |
| **④ 연구가설** | 이 과제가 검증하려는 것 | 근거 불필요 — **검증 방법이 필수** | 가설 + **어떻게 확인할 것인가** |
| **⑤ 목표·약속** | 우리가 달성하겠다는 것 | 근거 불필요 — **측정 방법이 필수** | 목표값 + **달성 판정 기준** |

**핵심 원칙**: "근거 없으면 못 쓴다"가 아니라 **"유형을 밝히고 그 유형에 맞는 것을 붙여라"**.

- ④에 실증을 요구하면 신규 연구 주제를 제안할 수 없다
- ①을 ④처럼 뭉개면 그건 조작이다
- **유형이 표시되지 않은 주장이 가장 위험하다** — 독자가 사실인지 희망인지 구별할 수 없다

**리서치 산출물**(`10-literature/`, `20-scenarios/`)은 ①만 다루므로 기존 verified/unresolved/refuted 3분류를 그대로 쓴다.
**계획서**(`50-grants/`)는 위 5유형을 쓴다.

공통 의무:
- 문서 끝에 **`미확인:` 한 줄** — 이번에 못 읽은 소스를 명시한다. 전부 읽었으면 생략
- 외부 서비스·API에 의존하면 **`third_party` 메타데이터**를 남긴다 (서비스명·라이선스 URL·확인일)

## §3 재현 가능성

- 산출물마다 **재현 명령**을 병기한다 — 이걸 어떻게 다시 만드는가
- 실행 환경(버전·의존성)이 결과에 영향을 주면 **고정하고 기록한다**
- 수치가 이전 회차와 달라졌으면 **왜 달라졌는지**를 쓴다. 조용히 갱신하지 않는다

## §4 검증 후 확인 (verify-then-ship)

- 산출물을 만든 **뒤에 다시 열어** 확인한다. 만들었다는 사실은 맞다는 증거가 아니다
- **"에러 없이 돌아갔다"와 "출력이 그럴듯해 보인다"는 정확성의 매우 약한 증거다**
- 자기 산출물을 자기가 승인하지 않는다 — `citation-reviewer`나 사람이 판정한다
- **검증 장치 자체도 검증 대상이다.** 통과시키는 검사기가 틀렸을 수 있다

# 재량 (골라도 되는 것)

## §5 서술 형태
문단형 산문 / key-value 불릿 / 표 — 독자와 용도에 맞게. 회의록·정리문서는 압축 구조, 대외 문서는 문단형.

## §6 시각 표현
색·폰트·레이아웃·차트 종류. 단 **데이터 형태에 맞는 차트**를 고르는 것은 §1의 연장이다.

## §7 분량과 깊이
요약본만 낼지, 부록까지 붙일지. 단 §2의 출처 표기는 분량과 무관하게 유지한다.

## 사인오프

산출물을 내기 전 아래를 한 줄씩 `PASS`/`ISSUE`로 표시한다. 산문으로 뭉뚱그리지 않는다.

```
데이터충실 PASS / 출처등급 PASS / 재현성 PASS / 검증후확인 PASS → 발행
```

ISSUE가 하나라도 있으면 중단하고 고친 뒤 다시 확인한다.
